## Acquisition-policy defect: do not adopt this workflow

[CelesTrak usage policy](https://celestrak.org/usage-policy.php), updated2026-05-22, requires downloading only needed data once per update and stopping machine queries after non200 responses. It endorses caching. The pinned run logs a last-30-days404 at`04:50:12.7509283Z` and continues with visual and many other queries. The workflow also uses automatic retries and fetches overlapping groups plus the full catalog. The GP documentation specifically discourages unnecessary overlapping collections. Therefore the mirror's whole acquisition implementation is **not a qualified policy-compliant acquisition template**.

That demonstrated operator defect is not, by itself, evidence that the basic-data blanket redistribution approval is revoked, or that downstream receipt of this immutable visual file is prohibited. Do not describe the operator as fully policy-compliant or adopt this mirror as an automatic production updater. Eventual transport selection needs its own bounded qualification.

## First-party alternative

Prefer one task-owned HTTPS fetch from the official CelesTrak visual-GP endpoint on an approved reachable transport, such as an owner-controlled Windows acquisition or task-owned GitHub runner. Preserve request URL/status/time, raw bytes/hash, LF-normalized derivative/hash, no retry after non200, and independent TLE validation. This avoids trusting a third-party snapshot and can independently compare whole-file content. It still requires a separately qualified acquisition/transfer and must not bypass provider access blocks. No such fetch was attempted here; no blocked CelesTrak download was retried. Direct Space-Track acquisition is another first-party option, but requires an authorized account, its access rules and separate credential/transport qualification; no account creation or access was performed.
